# Awards (phase 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Once-only coin-medal awards across the app: earned on the next qualifying event, celebrated in-app once, posted to followers (except private areas), shown on profiles with rarity, on web and iOS.

**Architecture:** A new `internal/awards` slice owns a static catalog (`award` leaf package), one rule per badge (SQL counts or a Go rule over all history), and `Service.Check` — a best-effort hook every logging service calls after its write. Earned badges are `achievements` rows (`kind='badge_earned'`, `category='awards'`, `source_key=<badge id>`, `private`, `celebrated_at`), so feed, kudos, blocks and the sharing switch keep working. Medal art is generated from one source file (`docs/medals/medals.json`) into a templ SVG component and a SwiftUI view.

**Tech Stack:** Go, Postgres, sqlc v1.31.1, goose, templ, htmx 4, templUI; SwiftUI, swift-openapi-generator.

**Spec:** `docs/superpowers/specs/2026-10-21-follow-awards-design.md` (sections "Awards", 4 badge engine, 6 medals, 7 iOS). Codebase map used to write this plan: phase-3 map in the session scratchpad (file:line facts are repeated below where a task needs them).

## Global Constraints

- **Catalog = the 31 badges in the spec table** (the "34" label miscounts it). IDs, areas and targets are fixed in Task 1's table; names and copy are the user's to change in the harness.
- **No bulk award at deploy.** No migration or job inserts badge rows for history. Rules count all history, but a rule runs only from a qualifying event (a hook after a successful write) or from the sweep for areas with a log in the user's last 24 h.
- **Once-only:** `UNIQUE(user_id, kind, source_key)` with `kind='badge_earned'`, `source_key=<badge id>`. No tiers, no XP (XP only reads `crew_challenge_met`, `internal/xp/db/queries.sql:62-69`; do not add `badge_earned` there), no push, never in nudges or coach replies.
- **Private areas:** nutrition, hydration, sleep, mind, body → `private=true`. A private row never reaches anyone but the owner: feed, kudos (`Visible`), profile, recap highlights (`OwnBetween`) and recap share.
- **`awards` sharing switch** is ON by default for everyone: `CREATE OR REPLACE FUNCTION sharing_on` with `'awards'` in the default list (`migrations/20261021130000_open_follow.sql:25-31`) and `achievement.DefaultShared()` in step. A PUT that omits `awards` keeps the stored value (copy `XP *bool`, `internal/achievements/api.go:125-149`). The web form gets a `share_awards` switch, because absent checkbox = off (`internal/social/handler.go:95-100`).
- **Wire compatibility:** `FeedItem.category` stays `training|streaks|goals` — stored `awards` is projected as `goals` in `projectFeed` only. Add only optional fields and new objects; no new enum values; never make a field optional or remove one. Every new `/api/v1` route goes into `docs/api/openapi.yaml` in the same commit.
- **Copy:** badge name and description come from the catalogue by badge id at read time, in the request's locale (web `awards.*` keys in new `internal/shared/i18n/{en,es,pt_pt,pt_br}_awards.go`, registered in the four `merge(...)` lists in `i18n.go:57-61`). The API returns localised `name`/`description`, so iOS ships no badge strings. Never render the stored English `title` of a badge row.
- **Hooks are best effort:** awarding never fails or slows the user's write beyond the rule queries; errors are logged at Warn inside `awards`, like `achievements.record` (`internal/achievements/service.go:70-78`).
- **One medal source:** area colours and glyph paths live in `docs/medals/medals.json`; web and iOS both render from it. Glyphs are lucide icon paths (ISC, the set templUI already vendors).
- Go tests: one persistent `GOCACHE=<session scratchpad>/gocache`; `TEST_DATABASE_URL=postgres://north:north@localhost:5434/north?sslmode=disable`. iOS: one persistent `-derivedDataPath <session scratchpad>/ios-dd`, `-skipPackagePluginValidation`. No push, PR or merge from implementers.

## Review Focus

1. A user with years of history and no new event earns nothing at deploy or from the sweep; their next qualifying log unlocks every crossed badge at once. → Task 2 (`TestNoAwardWithoutEvent`, `TestHistoryCountsOnNextEvent`), Task 3 (`TestSweepSkipsIdleAreas`).
2. A follower never sees a private badge: feed, kudos, profile, recap. → Task 4 (`TestPrivateBadgeNeverLeavesOwner`).
3. A shipped iOS build keeps working: PUT sharing without `awards` keeps it ON; a feed with badge items decodes with category `goals`. → Task 1 (`TestPutSharingWithoutAwardsKeepsIt`), Task 4 (golden + `TestBadgeFeedItemUsesLegalCategory`).
4. Several badges from one event make one feed card and one celebration, not N. → Task 4 (`TestOneCardPerMoment`), Task 6 (web modal lists all), Task 8.
5. A celebration shows once: after `seen` on one device it never shows on another; a failed `seen` is retried, not lost. → Task 4 (`TestUnseenThenSeen`), Task 6, Task 8.
